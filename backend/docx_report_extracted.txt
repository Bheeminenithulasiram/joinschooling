1. Introduction & Purpose

JoinSchooling is a unified education and career platform designed to bring together college discovery, internship discovery, application tracking, AI-assisted opportunity matching, and role-specific dashboards into a single ecosystem. Instead of a student searching separately across multiple websites for colleges, internships, and application status, JoinSchooling centralizes the entire journey — from account creation through logout — inside one authenticated, role-aware application.

This report documents that journey in complete detail: every step a user takes, every screen they land on, and every flow that connects sign-up to logout, for each role in the system (Student, Recruiter, College Representative, Mentor, and Admin).

1.1 Core Concept

Discover → Evaluate → Save → Apply → Track → Learn → Get Guidance

A student discovers an opportunity, evaluates it, saves it for later, applies, tracks the outcome, and uses AI-assisted discovery to keep finding better-matched opportunities — while colleges, recruiters, mentors and admins manage their side of the ecosystem in parallel.

2. System Architecture Overview

The platform is built as a modern three-tier web application. The frontend is a Next.js 15 application responsible for rendering role-specific dashboards and pages. The backend is a FastAPI service that owns all business logic, authentication, and authorization. The database is PostgreSQL, hosted on Neon, storing users, colleges, internships, applications, and saved items.

Figure 2.1 — High-level system architecture: browser → Next.js frontend → FastAPI backend → PostgreSQL (Neon).

Deployment: the frontend is hosted on Vercel, the backend API is hosted on Render, and the database runs on Neon's managed PostgreSQL service. Each layer scales and deploys independently.

4. Sign-Up (Registration) Flow

A new user begins on the landing page and chooses to register. They enter their basic details, and the system determines or asks for the account type (Student, Recruiter, College Representative, or Mentor). Details are validated on both the client and the server before the account is created.

Figure 4.1 — Step-by-step sign-up flow, from the landing page to redirect-to-login.

4.1 What happens on the server

The submitted email is checked for duplicates.

The password is hashed (never stored in plain text).

The role is recorded against the new user record.

A confirmation response is returned and the user is redirected to Login.

Known gap: registration currently behaves primarily around the student flow. It should be explicitly extended so every role (Recruiter, College Representative, Mentor) has an equally first-class registration path rather than being treated as a variant of student sign-up.

5. Login & Role-Based Redirect

Login takes an email and password, validates them against the stored hash, and — on success — issues authentication tokens and resolves the user's role so the frontend can send them to the correct dashboard.

Figure 5.1 — Login flow: credential validation, token issuance, role resolution, and dashboard redirect.

6. Authentication Architecture (JWT)

Authentication is based on JSON Web Tokens. On successful login the backend issues a short-lived access token and a longer-lived refresh token. The access token travels with every subsequent API request; when it expires, the frontend silently exchanges the refresh token for a new access token so the user's session continues without interruption.

Figure 6.1 — JWT access/refresh token lifecycle across a session.

6.1 Security Principle

Frontend role checks exist for user experience only. The backend independently re-validates the user's role and resource ownership on every request — hiding a button from a student is not a security control by itself; the backend must also reject a Student calling an Admin-only endpoint.

7. Protected Routes & Authorization

Every page in the authenticated application is a protected route. Before rendering, the frontend checks that the user is logged in and that their role is permitted to view that page. The backend performs the equivalent check independently for every API call, and additionally verifies resource ownership (for example, a Recruiter may only edit internships that belong to their own company).

22. Security Architecture

Password hashing — passwords are never stored or compared in plain text

JWT access + refresh tokens for session management

Protected routes on the frontend for user experience

Backend authorization as the real security boundary, re-checked on every request

Resource-ownership checks (e.g. a Recruiter cannot edit another Recruiter's internship)

Rate limiting and security headers on the API

The guiding principle: frontend checks are for experience, backend checks are for security. Both must exist, but only the backend check can actually be trusted.

23. Known Implementation Gaps

The platform already has a substantial working implementation, but the following areas are explicitly still being hardened and should not be treated as complete:

Registration is currently oriented around the student flow and needs equal support for all roles.

The College Representative ↔ College relationship needs to be properly modeled and enforced.

Recruiter ↔ Company ownership needs to be consistently enforced at the API layer.

Google OAuth buttons exist in the UI, but the full OAuth flow is not yet complete.

Some dashboard sections still show demo/fallback data instead of live production data.

Database setup still shows SQLite-oriented patterns; a formal migration tool (Alembic) is needed for PostgreSQL/Neon in production.

25. Conclusion

JoinSchooling's value is in unifying a journey that is normally scattered across many disconnected websites: college research, internship search, applications, saved shortlists, and career guidance, wrapped around role-specific dashboards and an AI layer that retrieves real data rather than inventing it. The architecture — Next.js, FastAPI, PostgreSQL, JWT authentication — is a sound foundation. The immediate priority is hardening the gaps in Section 23 (multi-role registration, ownership enforcement, OAuth completion, and production-grade migrations) so every dashboard shown in this report is backed by real, correctly-scoped, backend-authorized data.
